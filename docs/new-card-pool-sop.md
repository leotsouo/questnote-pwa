# 新卡池發布 SOP

## 第一步：先同步並核對最新正式版本

**需求訪談與企劃之前，先同步最新正式版。** Fetch 最新 `origin/main`、`gh-pages`，讀取正式 HTTPS 的版本、release descriptor／artifact manifest，核對部署 commit、artifact ID、reviewed source commit 與核對時間。來源 main 最新不等於正式版最新；記錄 main 尚未發布的差異及處理方式，不把生成的 gh-pages 複製回 source。

從最新 `origin/main` 建立乾淨 `codex/` 功能分支，先完成必要 runtime／契約支援，再以核對過的內容建立新的 authoring workspace。若有未發布內容，先完成 reconciliation；不可混入本池且未經驗收。舊 workspace 的 baseline、receipts、卡圖和 candidates 不重寫。

此 SOP 從下一池開始。蜜光糖庭與既有正式內容不補做；歷史 workspace／candidate 保持原格式。

## 固定訪談與預設

已提供的資訊直接帶入，一次詢問以下三題，每題可回答「交給你」。不要詢問 repository 可判斷的工程細節。

1. **主題與感覺**：這次的文化、地域或故事方向是什麼？希望玩家感受到什麼情緒？
2. **角色與美術**：必須出現哪些動物、代表角色、指定稀有度、畫風或禁止元素？數量是否沿用預設 12 隻？
3. **特殊體驗**：是否指定新探險地區、特殊解鎖、贈寵或特別演出？沒有指定就由 AI 評估。

回答後由 AI 完成企劃、名單、Lore、提示詞、食物、專長、地區方案與動畫。預設一池、12 隻可調整，稀有度由 AI 配置；兩隻 UR 不是通用規則。沿用現行价格、機率與保底，全部第一抽開放，不新增解鎖或贈寵。特殊要求寫進 brief。

企劃先定義池級故事：主要衝突、角色彼此的關係、不能觸碰的題材或畫面禁忌，以及這些決策如何落到角色名單、地區與動畫。企劃階段只確定方向、規格與待驗假設；進入實作後才製作素材、接入受控 runtime、量測實際畫面。若企劃要求新資料模型或跨系統功能，先完成獨立規格與相容性評估，不以每池例行項目直接擴大範圍。

在 brief 記錄 `imageReviewMode: "human" | "ai-self"`。新池明確選擇；舊 brief 缺欄位時按 `human` 處理。`human` 保留中途人工審圖；`ai-self` 由 AI 製作並自審內容、卡圖與動畫，使用者在最後只看確切整包的驗收摘要與發布決策，不展示卡圖或動畫給使用者作中途審核。

## 每池同時發布的內容

| 內容 | 必須完成 |
| --- | --- |
| 一個卡池／系列 | 名單、稀有度、卡圖、Lore、對話與角色資料 |
| 一種新工坊食物 | 唯一新 ID、名稱、配方、效果、材料來源、實際適合的新角色 |
| 每隻寵物的偏好 | 明確 tags 與理由；空偏好也須说明，不從名稱猜測 |
| 每隻寵物的探險專長 | 角色定位、專長角色與用途，核對實際派遣結果 |
| 卡池動畫 | 必須選擇專屬或沿用動畫，寫明選擇理由、分鏡、時長、稀有度效果、略過與減少動態；禁止無動畫或 `animationKey: "none"`。主題只決定視覺，不改變共用前奏時長。 |
| 探險地區評估 | `add` 或 `reuse` 及理由；新增時完成故事、派遣、獎勵、里程碑與專屬地區圖片，沿用時列出材料供應地區 |
| 發布說明 | 角色、食物、專長、動畫、地區變更及實際驗收證據 |

食物優先使用現有材料，預設使用既有主題食物尺度：普通送禮 +75、符合偏好時總共 +150，不能疊加；保留每日贈送與交易限制。

專長包括探路 `scout`、採集 `gatherer`、同行 `companion`、解讀 `scholar`、守護 `guardian`。目前 runtime 依角色資料推導，SOP 記錄預期角色與理由並比對 `getPetSpecialty()`，不把企劃文字當成有效設定，也不改變舊寵物專長。若要新增類型或獨立指定方式，先完成受控 runtime／契約，再鎖定 authoring。

新地域具有獨立故事，且有探索、獎勵或材料用途時新增地區；只有美術題材差異可沿用。標準發布最多一個新地區。新增地區包含可實際使用的解鎖條件、派遣時間／能量、獎勵、材料用途、探索發現、故事及 10／25／50／75／100 五個里程碑。新增材料須有可領取的來源與食物配方用途。決定新增後不能以未完成名稱、fallback 故事或臨時示意圖交付。

### 新增探險地區的圖片是必交項目

企劃階段即列入專屬地區插畫、提示詞、生成工具及費用依據。依下方費用原則確認後產圖；保存原圖、提示詞、生成紀錄與輸出 SHA-256。畫面需呈現地區辨識地標、故事衝突或探索動作、可見環境結果，以及小圖裁切限制。除使用者明確指定其他形式外，交付生成的完整點陣插畫；簡化 SVG、佔位圖、其他地區舊圖或寵物卡圖不能充當完成品。

正式使用 `assets/expeditions/<areaId>.webp`，靜態 16:9、至少 960 × 540，地圖小卡與派遣視窗使用同一資源。圖片與角色卡圖採同一 brief 審圖模式，不增加第三次人工關卡；AI 須實際打開兩個畫面，檢查桌面與手機的載入、裁切、地標辨識及閱讀，並將結果納入最終整包證據。保留圖片失敗時的操作能力，核對 artifact manifest、Service Worker precache 與離線載入。

`npm run images:check` 必須完整解碼每個地區 WebP，拒絕缺圖、損毀、偽裝副檔名、尺寸或比例錯誤、缺少 source precache。Assembler 對有效 companion catalogs 再驗證實際圖片，新增地區但未附圖時不得產生 artifact；CI 同步執行圖片检查。在 `checks.region.evidence` 寫入圖片路徑／hash、製作紀錄、實際雙畫面與手機／桌面／離線驗證。檔案存在或提示詞齊全不代表視覺驗收通過。既有不可變 receipts 和 candidates 不回填或重寫。

卡池背景配色也須與目前已上線卡池並排比較，確認本池的主題可辨認，並檢查各 App 主題下的文字對比與手機版面；不能只更改低優先級 CSS 而未核對實際 computed style。

## 故事如何成為卡圖

**每隻角色都以「辨識特徵＋故事動作＋可見結果」設計卡圖。** 玩家在沒有讀到名稱與 Lore 時，也應能看出牠的特殊之處；名稱、來源、個性與能力都要有適合的畫面線索。這是所有稀有度的共同標準，由 AI 在既有 plan／content／prompts 階段完成，不增加前期人工關卡。

### 先取材，再設計畫面

1. 核對題材的故事、動物、稱號或器物，找出讀者／愛好者會認出的關鍵。文化與作品題材要分清原作事實、象徵轉化及遊戲原創；需要查證的來源留下引用。
2. 每隻先選一至兩個主要辨識點，如巨翼、白眉、肉角、茶花偏好、藏卷或劍術，保留可辨認的物種外形。依本池世界觀創作故事，讓牠有具體想守護、完成或學會的事。
3. 從故事挑一個可畫的時刻，決定姿態、相關道具與周遭反應。動作可以是試橋、回望、展卷或鎮守；安靜角色也能藉風、水、雨珠與落葉的變化表現力量。
4. 檢查名稱中的關鍵意象是否可見。例如「劍猿」應有清楚的劍、劍勢或可辨認的劍術媒介；道具必須與故事相連。若新增原創道具，同步寫進 Lore 與角色描述，註明和取材來源的差異。

逐隻在 `plan.json` 的 `design` 寫清楚以下內容，並帶入對應提示詞；可另附故事／美術對照表供審圖，但不能只把必要設計留在旁註裡。

| 設計層次 | 要回答的問題 |
| --- | --- |
| 辨識特徵 | 哪個外形或物件能讓玩家認出這個角色的來源與名字？ |
| 故事動作 | 牠此刻正在做什麼，為什麼這個動作符合牠的故事？ |
| 可見結果 | 風、水、光、植物、路徑或道具如何回應牠，讓能力與個性可見？ |
| 構圖與限制 | 主角、動作與關鍵道具如何在小卡中讀清楚？哪些物種特徵要保留，哪些混種或誤讀要避免？ |

### 以稀有度安排氣勢與演出

- **UR**：呈現本池主角的地位與傳奇分量。適合神獸／武俠主題時，可以有坐鎮一方的威儀；用姿態、視角、力量範圍及環境反應支撐，各隻有自己的氣質，如巨翼鎮風、不動守界或精準劍勢。其他主題依其情緒表現同等分量，不固定套用霸主姿態。
- **SSR**：以獨特能力、器物或傳承形成記憶點，例如展卷連到實景、寒氣收在葉緣、水下找回失物。
- **SR**：把招牌本領畫成明確動作，例如極速拉繩渡溪、回聲引路、獅吼清開障礙。
- **R／N**：以較輕的動作與生活細節講故事，例如試踩橋板、回首等候、辨雨護芽、茶花眠香。仍須有自己的辨識點。

氣勢不只由體型與特效大小決定：小動物也能以沉靜姿態、受控界線與環境對照表現強大。同池維持畫風、材質、色彩語言的一致性，同時讓場景、光線與動作符合各自故事。

### 借氣質時，保留角色本體

引用另一種神獸或文化象徵的氛圍時，先拆解成可借用的視覺語言，例如幽深水色、低重心、對稱、莊嚴與鎮守感；物種融合另依 brief 決定，不能因借用氛圍就自動增加混種器官。本池朱蛤借玄武的沉穩深水氣質，仍保持蟾蜍的頭、疣粒皮膚與四足。

劍隱山河第三版的參考思路：重岳雕以完整展翼、守橋姿態與無鋒重劍呼應重量及承諾；鎮嶺蛤以黑岩、朱息界線和內外水霧對照表現毒王的控制力；素心劍猿以直劍、劍勢分葉及初學竹枝連結名稱與傳承。這些是設計方法的案例，未來依新主題重新發想。

### 提示詞、產圖與審查

提示詞先寫物種與辨識點，再寫具體動作、關鍵道具、可見結果、構圖、光線及禁止元素。避免只用「帥、好看、神獸感、霸氣」等形容詞取代畫面指令。負面提示詞要逐隻檢查，不能禁止角色必需的劍、書卷或動作。

AI 先完成關鍵角色的構圖，實際縮至卡片尺寸檢查辨識度與故事表現，通過後再延伸全池；生成後逐張對照實際圖片與設計，不能只根據提示詞宣稱達成。至少檢查物種與肢體、完整翼尖／尾端／劍尖、臉與道具是否被遮、縮至實際卡片尺寸後的辨識度，以及故事動作與結果是否可見。局部瑕疵可定向修正，構圖或故事表現不足時重新構圖；保留原圖、修正版及實際生成紀錄。

`human` 模式交付審圖頁逐張展示卡圖、來源／原創差異、辨識特徵、故事動作與結果，提供可展開的 Lore；修訂時提供前版比較。人工審圖除風格與輪廓外，也確認名稱、故事與卡圖是否一致，以及各稀有度的演出是否合適。`ai-self` 模式由 AI 在同等實際畫面自審並留存逐張紀錄，不向使用者展示卡圖。內容或圖片修訂仍依下方既有 exact-hash 規則重新審核受影響階段。

選定素材時記錄來源、用途、選定版本、原始檔與輸出檔 SHA-256，以及其所屬 brief／candidate／artifact；修訂時保留前版與取代原因。圖片、地區插畫與動畫資源均可由這些紀錄追回實際 bytes，不以檔名或提示詞代替版本證據。

## 產圖外掛與費用原則

**盡量使用已安裝且適用的產圖外掛插件，避免額外費用。** 開始產圖前先盤點可用工具／外掛及參考圖支援，確認其計費方式與目前可用權限。優先使用已確認不會額外計費的外掛；安裝了外掛不代表呼叫免費。

費用無法確認時不呼叫，改用已確認免費／不額外計費的現有方案；沒有可用方案時回報阻礙，不自行啟用付費 API、訂閱、購買額度或安裝付費依賴。每隻角色提示詞的 `provenance` 記錄實際 `tool`、`noExtraCost: true`、`costBasis`，並保存可用的模型、reference、seed 等資訊，未知資訊不編造。動畫優先本地 CSS／SVG。

## 階段與審核模式

正式版本同步 → 固定訪談 → AI 企劃與製作 → 依 brief 模式審圖 → staging／整包驗證 → **人工最終整包驗收與明確「可以發布」** → 正式發布驗證。

保留 brief／plan／content／prompts／images 五個 exact-hash gates。前四階段由 AI 審查，記錄 `reviewerType: ai` 和真實 reviewer；images 依 archived brief 的 `imageReviewMode` 記錄真實 reviewer：`human` 與缺欄位舊 brief 要求 `reviewerType: human`，`ai-self` 要求 `reviewerType: ai`。release review 嚴格比對 brief 模式與圖片 receipt。只有明確標記 synthetic 的測試可用 synthetic reviewer，不能用來取得真實發布就緒。

卡圖審查涵蓋角色識別、風格、裁切與提示詞／Lore 一致性。相同 PNG bytes 可記錄原模式的核准及 SHA-256 沿用；圖片變更重新核准。工具或上游內容變更仍需重跑受影響階段，不覆寫舊 receipts、snapshots、candidates 或發布產物。

現行 SOP 的 `ecosystem.json` 與寵物內容一起進入 content hash；baseline 包含工坊、偏好、材料、探險資料與相關 runtime。缺少新食物、材料來源、逐隻偏好／專長、地區評估、完整新增地區或費用依據，都阻擋核准／staging。`pipeline.json` 的 SOP marker 不可移除降級。

candidate 保存原 companion baseline bytes、審核輸入與合併後 companion catalogs；assembler 重新驗證，preview 和 production 使用同一組內容。來源 companion 檔案只可等於原 baseline 或本次完整核准結果，其他漂移會被拒絕。

## 整包驗收與正式發布

執行 `npm test`、JS 語法檢查、`npm run pools:validate`、`npm run images:check`、`npm run test:pool:release`。新增內容時，不用固定總數取代資料引用、專長、偏好及地區覆蓋檢查。

採用圖像選池列的版本，新池整包須同步 `src/poolDirectory.js` 的 `POOL_NAVIGATION.featuredPoolId`，並驗證新池封面置前且標示「新登場」、「全部系列」畫廊仍可直接點選歷代 active 系列，無須輸入搜尋。推薦指向隨核准整包發布，不先單獨更改正式站；推薦曝光不修改候選、價格、解鎖、各池保底或已儲存選池。推薦期日期與倒數須依後續定版政策設定，不由目錄順序猜測。

推薦期功能使用同一設定的 `recommendation: { startsAt, endsAt }`，兩者均為包含時區的 ISO 時間，目標長度 14 天。首次推薦從該功能正式上線生效，不追溯既有系列發布日；日期未定時保持 `null`，不得用建置時間或每個玩家首次開啟時間替代。發布前確認截止日、台灣時間顯示、到期仍可抽取和保底保留。到期只移除推薦曝光，絕不把 `active` 設為 false。發布延期時重新確認排程與 artifact，詳見 [生命週期改善計畫](card-pool-lifecycle-plan.md)。

在隔離 preview 實際驗證：入場／單抽／十連／SSR／UR 順序與重複角色、各階段略過／連點／鍵盤／減少動態／圖片失敗與中斷；工坊製作→選角送禮；逐隻專長與派遣效果；新增地區解鎖→派遣→領獎→里程碑；無重抽／重複扣款／領獎、存檔相容及 service worker 更新。不要操作正式玩家 DB 或把 synthetic 測試結果當成實際卡池驗收。

### 卡池畫面與動畫的共同驗收規格

以下規格源於 V3.5.14 完整 App 記憶體試演的修正；工程實測與人工最終驗收分開記錄。後續每池沿用同一組規格，若主題需要例外，先明確記錄理由及實際畫面，再納入既有整包驗收。不可逐池複製 CSS 偏移量，也不可只憑程式碼或靜態圖片宣稱動畫順暢。

| 項目 | 固定規格與通過條件 |
| --- | --- |

### 動畫檢視與證據

最終整包驗收前，必須製作可操作的動畫檢視頁並由 AI 實際檢查。`human` 模式主動開啟並提供使用者可重開的連結；`ai-self` 模式只保留內部檢視頁與證據，使用者不看動畫。不能只交文字說明、靜態卡圖或自動測試紀錄，也不能要求耗費星塵、抽到稀有角色才能檢視。

播放頁直接使用待發布 artifact 的實際動畫模組、樣式、卡圖與 presentation 資料，標示 artifact ID；展示用固定結果與真實抽卡交易分開，不呼叫抽卡、扣款、收藏、保底或補償 API。至少提供完整入場、切換卡池完整登場、單抽、十連、每一隻 UR，以及所有有演出的 SSR；十連包含重複角色以查看揭露順序。提供正常／減少動態切換、重播、略過與繼續操作。

明確標示哪些演出為新作或沿用；沿用時說明實際場景與文案，不把改名或換圖說成專屬動畫。所有卡池都要有可播放的前奏，正常模式固定 3000ms；依主題改造視覺時不可更改時長。先確認播放按鈕可用、圖片載入、手機版面與播放後可再次操作。`human` 模式再開啟頁面請使用者檢視；`ai-self` 模式由 AI 自審並只向使用者提供整包結論。在 `checks.animation.evidence` 記錄播放頁、artifact ID、實測紀錄及證據環境（source 試演、隔離 preview、production artifact、正式 HTTPS 或真機）；只有實際完成的環境可標為通過。若提出修改，重建受影響產物並檢視最新版本後才能發布。

final review JSON 包含 `schemaVersion: 1`、`sourceCommit`、`candidateId`、`candidateManifestSha256`、`previewUrl`、`artifacts.preview/production`（`artifactDir`、`artifactId`、`manifestSha256`、`scopePath`），及 `checks.animation/workshop/specialties/region/transactions/serviceWorker`（`status: pass`、實際 `evidence`；沿用地區可 `status: reuse`）。

執行 `node scripts/poolReleaseReview.mjs <evidence.json>`，取得綁定整包的 `packageHash`。每項 `checks.*.evidence` 明示實測環境與 artifact／來源 pin，區分工程通過、使用者核准與尚待真機或正式 HTTPS 驗證。人工最終驗收寫入 `humanAcceptance: { reviewer, acceptedAt, packageHash }`；明確發布授權寫入 `publicationAuthorization: { reviewer, approvedAt, packageHash, phrase: '可以發布' }`。同一次使用者對確切整包說「可以發布」可記錄兩者；`ai-self` 不要求使用者中途看卡圖或動畫。沒有明確發布同意就等待。

重新執行檢查須 `releaseReady: true`；缺少驗收／授權時 CLI 回傳非零 exit code。任何卡圖、內容、來源、預覽或 production artifact 的實質修改，都重建受影響產物並重新驗收最新 packageHash。紀錄不是數位簽章，工具不能替代真實人工同意，也沒有發布命令。

核准後才合併發布來源、推送核准的生成產物。記錄來源 PR／merge、部署 commit、Pages 成功、正式 HTTPS bytes／hashes 與 service worker 更新結果；保存舊產物與歷史證據。不把 source merge 當成已發布。
